## Ajustes posteriores (feedback de uso, 2026-08-06)

Seis correcciones de interacción sobre la feature ya cerrada. Ninguna toca el modelo de datos, la RLS ni las funciones puras de rango y layout.

- [x] **A1 — El desplegable tapaba su propia etiqueta.** `SelectContent` usaba `alignItemWithTrigger` (el default de Base UI), que posiciona el popup con la **opción seleccionada encima del trigger**, estilo select nativo de macOS: al abrir "Desarrollador" se leía `Desarrollador: todos ✓` pisando la etiqueta. Ahora abre debajo (`alignItemWithTrigger={false}`, `align="start"`) y la primera opción dice solo `Todos`.
- [x] **A2 — Cursor.** `cursor-pointer` en `SelectTrigger` y `SelectItem` de `src/components/ui/select.tsx`, como ya hacía `buttonVariants`. Alcanza también a los formularios de `/admin/*`.
- [x] **A3 — Filtros interconectados.** Las opciones salen de las reservas del rango visible (`getFilterFacets` + `deriveFacets`), no de los datos maestros completos: elegir un desarrollador acota los otros selects a sus clientes y proyectos reales.
  - **Cada faceta se calcula excluyendo su propio filtro.** Es lo que hace usable el filtrado facetado: si la faceta de desarrollador se acotara a sí misma, quedaría una sola opción y no habría forma de cambiar de dev sin limpiar todo. Hay un test unitario dedicado a eso.
  - Una sola query por render, con las cuatro facetas derivadas en JS sobre las mismas tuplas — mismo criterio que `getDayLoad`.
  - Cuando el rango no tiene reservas, el select queda deshabilitado con el texto `Sin opciones`, en vez de un desplegable vacío que se lee como roto.
- [x] **A4 — `Limpiar filtros` en su propia línea**, debajo de los seis filtros. Como hijo del `flex-wrap` saltaba de lugar según cuántos filtros hubiera activos.
- [x] **A5 — Feedback al filtrar.** Antes, entre el click y la respuesta del servidor no cambiaba nada en pantalla: el select seguía mostrando el valor viejo, porque el valor se lee de la URL y la URL todavía no había cambiado. Ahora `useOptimistic` muestra la elección al instante, y un provider compartido (`calendar-pending.tsx`) marca los resultados con `aria-busy`, les baja la opacidad y anuncia `Actualizando…` en una región `aria-live`. **Verificado en el navegador frenando la navegación a propósito**, porque en local el estado intermedio pasa demasiado rápido para observarlo.
- [x] **A6 — Contenido del bloque.** Se sacó el horario (la posición y la altura ya lo dicen) y se agregó el cliente en una segunda columna, no en una cuarta línea. Medido a 1280px: una reserva de una hora mide 152×48px y muestra desarrollador, proyecto y cliente **sin recorte**. El horario sigue en el popover y en el nombre accesible. Esto acerca el bloque a la spec funcional §4.2, que pide desarrollador, proyecto, cliente, franja y estado.
  - **Efecto colateral corregido:** el mensaje de "sin resultados" resolvía los nombres desde las facetas, que justo en ese caso pueden venir vacías. Ahora los busca por id (`getSelectedFilterNames`), así el mensaje sigue diciendo *cuál* filtro esconde los datos — que es todo el punto de ese estado (`DESIGN.md` §9).
